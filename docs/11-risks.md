# 11. 리스크와 대응

가능성과 영향은 상·중·하로 표시한다. 법규 항목은 설계자의 이해를 정리한 것이며 법률 자문이 아니다. **실서비스 전에는 전문가 확인이 필요하다.**

## 1. 기술 리스크

| ID | 리스크 | 가능성 | 영향 | 대응 | 대체안 |
|---|---|---|---|---|---|
| T1 | ESP-IDF 5.3과 esp-tflite-micro·esp32-camera 컴포넌트 버전이 맞지 않거나 빌드가 실패함 | 중 | 상 | `idf_component.yml`에 버전 고정. 펌웨어를 일정 초반에 배치하고, 처음에는 더미 모델로 빌드부터 통과시킴 | 컴포넌트 예제 프로젝트(person_detection)에서 출발해 수정 |
| T2 | int8 양자화로 정확도 하락 | 하 | 중 | 대표 데이터 200장, CI 게이트 2%p | 양자화 인식 학습(QAT) |
| T3 | 추론이 추정보다 느림 (ESP-NN 미적용 등) | 중 | 중 | `CONFIG_NN_OPTIMIZED` 확인, 부팅 시 추론 시간 로그 | 입력 64×48로 축소, 채널 수 감소 |
| T4 | 밀착 정확도 0.70 미달 | 중 | 중 | 밀착 데이터 과대 샘플링, 어려운 샘플 재학습 | 출력 간격 4 (24×18 격자), 병합 거리 축소 |
| T5 | 합성 → 실제 영상 도메인 갭 | 상 | 상 (실설치 시) | 범위 밖임을 명시. 정확도는 합성 기준으로만 주장 | 실제 데이터 소량 미세조정, MobileNetV2 백본 (B안) |
| T6 | 카운트 오차가 누적돼 매장 내 인원이 틀어짐 | 중 | 중 | `count_anomaly` 알림, `occupancy_resets` 기준점 | 정기 기준점 초기화 (예: 매일 점검 시각) |
| T7 | **장기 체류 확정이 붐빌 때 지연됨** (구조적) | 확정 | 중 | 감수하기로 결정. 심야 체류 알림이 보완. TC-12로 동작 고정 | 실서비스에서 입·퇴장 인증 세션 토큰 (개인 식별 없이 정확) |
| T8 | 기기 IP가 바뀌어 실시간 뷰 연결 실패 | 중 | 하 | 서버가 매 요청의 출발지 IP를 `last_ip`로 갱신 | 공유기 DHCP 고정 할당 |
| T9 | 카메라 모드에서 스트림 인코딩이 추론 FPS를 깎음 | 중 | 하 | 스트림 4 FPS 제한, 코어 분리 | 실시간 뷰 끄기 (`CONFIG_DOORKEEPER_LIVE_VIEW=n`) |
| T10 | 카메라 모드에서 SNTP가 실패해 이벤트 시각이 틀림 | 하 | 중 | SNTP 동기화 전에는 이벤트 전송 보류 | 서버 수신 시각으로 대체하고 표시 |
| T11 | CI 시간 초과 (TF 설치, ESP-IDF 이미지 다운로드) | 중 | 하 | pip 캐시, 잡 타임아웃 설정 | `tflite-runtime` 계열 경량 패키지로 평가 |
| T12 | 기기 다운 (힙·스택·워치독·브라운아웃) | 하 | 중 | 정적 할당, 상태 로그, 자동 재부팅 + boot 이벤트 (`04-model.md` 1.8절) | 소크 테스트에서 원인 확인 |

## 2. 일정 리스크

| ID | 리스크 | 가능성 | 영향 | 대응 |
|---|---|---|---|---|
| S1 | **3시간 안에 범위를 다 하지 못함** | 상 | 상 | 시간 상자와 체크포인트 운영, 미리 정한 순서대로 범위 축소 (`12-schedule.md`). 필수 조건 3개를 먼저 끝냄 |
| S2 | 보드 인식, 플래시, USB 문제 | 중 | 상 | 첫 10분에 hello_world 플래시로 확인. 현재 `/dev/cu.usbmodem*`가 없음 (보드 미연결 상태) |
| S3 | 학습이 잘 수렴하지 않음 | 하 | 중 | 학습을 백그라운드로 돌리면서 서버 작업을 병행. 1회만 재시도 |
| S4 | 펌웨어 디버깅이 길어짐 | 상 | 상 | 1:55에 펌웨어 체크포인트. 늦어지면 실시간 뷰와 대시보드 부가 기능부터 축소 |

## 3. 개인정보 리스크

| ID | 리스크 | 대응 |
|---|---|---|
| P1 | 카메라 모드 실시간 뷰에 실제 사람이 찍힘 → 영상정보 처리 | ESP32에서 브라우저로 직결 (서버 경유 없음), 녹화 없음, LAN 한정, 토큰, 동시 1명, 기능 끄기 가능 (`02-architecture.md` 1.6절) |
| P2 | DB 기록(시각·방향·인원)을 CCTV·결제 기록과 결합해 식별 | 개인정보에 준해 관리. 회원 ID 저장 안 함, 결제는 집계만, 보존 30일, 운영자만 접근 |
| P3 | 적은 인원 통계가 한 사람을 가리킴 | 외부 공유 시 3명 미만은 가림 |
| P4 | 대시보드·설정 API에 인증이 없음 (LAN 데모) | 실서비스에서는 로그인과 HTTPS 필수. 설정 변경은 `settings_log`로 추적 |
| P5 | 디버그 목적의 영상 저장 유혹 | 녹화 기능 자체를 만들지 않음. 서버 API에 이미지 필드 없음 (TC-19) |
| P6 | XIAO ESP32-S3 Sense 보드에 마이크가 있음 → 녹음 가능성 | 펌웨어가 마이크(PDM)를 초기화하지 않음. 코드 리뷰 항목으로 둠 |

## 4. 법규 리스크 (실설치 시, 확인 필요)

| ID | 관련 내용 | 이 설계의 대응 | 확인할 것 |
|---|---|---|---|
| L1 | 개인정보보호법상 공개된 장소의 고정형 영상정보처리기기 설치·운영 제한 (목적 제한, 안내판 설치, **녹음 금지** 등) | 출입 계수·안전 목적으로 한정, 녹화·녹음 없음 | 안내판 문구에 계수 카메라임을 고지. 기존 CCTV 안내와 통합할지 |
| L2 | 생체인식정보 등 민감정보 처리 | 얼굴 인식·외형 재식별을 하지 않기로 결정 (`02-architecture.md` 1.6절) | 결정이 유지되는지 변경 시 재검토 |
| L3 | 보존 기간과 파기 | 원시 이벤트 30일, 알림 90일, 기기 로그 14일, 매일 정리 작업 | 매장의 CCTV 보관 정책과 일치시킬지 |
| L4 | 자동화된 판단으로 인한 불이익 | 알림 문구는 "의심, 확인 권장"으로 하고 최종 판단은 사람이 함. 개인을 지목하지 않음 | 알림을 근거로 한 조치 절차를 운영 정책으로 정할지 |
| L5 | 무선기기 인증 (전파법) | 데모 단계라 해당 없음 | 제품화 시 사용 모듈의 국내 인증 여부 확인 |

## 5. 결정 근거

- **T7을 "확정"으로 둔 이유**: 개인 식별·재식별을 하지 않는다는 결정의 직접적인 결과다. 숨기지 않고 테스트(TC-12)와 비교 실험(E2)으로 드러낸다.
- **S1을 최상위로 둔 이유**: 1명·3시간이라는 여건이 다른 모든 리스크보다 결과를 크게 좌우한다.

## 6. 대안과 트레이드오프

| 대안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| 리스크를 점수화 (가능성 × 영향) | 우선순위가 정량적 | 3시간 프로젝트에서 과잉 | 상·중·하로 충분 |
| 법규 검토를 생략 | 시간 절약 | 실설치 가정 설계에서 핵심 제약을 놓침 | 기각 (확인 목록 형태로 유지) |
