# 01. 요구사항 정리

> 무인가게 출입 이상 감지 시스템 (edge-doorkeeper)
> ESP32 카메라가 사람이 **누구인지**가 아니라 **몇 명이 어느 방향으로 지나갔는지**만 판단하고, 그 결과를 (모의) 출입 인증 기록과 대조해 이상 상황을 감지·태깅한다.

## 0. 프로젝트 여건

| 항목 | 내용 | 설계 영향 |
|---|---|---|
| 인원·기간 | 1명, 3시간 (설계 + 구현 + 데모 전체로 가정) | 필수 조건 3개를 증명하는 **최소 동작 시스템(MVP)**으로 범위 축소 |
| 보드 | Seeed **XIAO ESP32-S3 Sense** 보유 (ESP32-S3R8: PSRAM 8MB, Flash 8MB, OV2640 카메라, microSD 슬롯) | 추가 구매 없음. 카메라 센서 모델은 보드 리비전 확인 필요 |
| 예산 | 0원 | 비교 실험용 센서(IR 빔 등)는 **시뮬레이션으로만** 비교 |
| 테스트 환경 | 직접 생성한 **합성 천장뷰 모의 영상** | 정확도는 합성 데이터 기준으로만 주장, 실매장 성능은 주장하지 않음 |
| 출입 인증 장치 | 없음 | 시나리오 파일에서 만든 **모의 인증 이벤트**로 대체 |

## 1. 결정 사항

### 1.1 핵심 데이터 흐름 (MVP)

```
[합성 천장뷰 영상 생성기] ──▶ 프레임(.bin) → ESP32 microSD/Flash
                         └──▶ 시나리오 정답 + 모의 인증 이벤트(JSON)
ESP32: 프레임 재생 → int8 모델 추론 → 추적·라인 통과 판정 → 이벤트 HTTP 전송
서버: 이벤트 수신 → SQLite 저장 → 규칙 엔진(동반입장/장시간 체류) → 알림 기록
브라우저: 대시보드(서버에서 숫자만 받음) + 실시간 뷰(ESP32에서 직접 받음, 저장 안 함)
```

### 1.2 기능 요구사항

| ID | 기능 | 우선순위 | 비고 |
|---|---|---|---|
| F1 | ESP32 온디바이스 추론: 프레임별 사람(머리) 위치 추정 | **반드시** | 필수 조건 1 |
| F2 | 추적 + 가상 라인 통과로 **인원 수·방향(IN/OUT)** 판정 | **반드시** | 후처리는 ESP32에서 수행 |
| F3 | 통과 이벤트·시스템 로그(부팅, 추론 지연, 오류)를 서버로 전송 | **반드시** | |
| F4 | DB 저장: 통과 이벤트, 모의 인증 이벤트, 알림, 시스템 로그 | **반드시** | 필수 조건 2 |
| F5 | **동반입장 감지**: 인증 1회 후 시간 창(예: 5초) 안에 IN이 2명 이상이면 알림 | **반드시** | 인증 시각과 통과 시각 대조 |
| F6 | **장시간 체류 감지**: T분 이상 머문 사람이 **확실히** 1명 이상이면(확정값 ≥ 1) 알림. 심야(00~05시)에 매장 내 인원이 0보다 커도 알림 | **반드시** | 확정값 계산은 `07-database.md` 4.2절. 데모에서는 시나리오 시간 압축 |
| F7 | **CCTV 검색 보조**: 이벤트 종류·기간별 시각 목록 조회 API | **반드시** | 예: `GET /v1/events?type=tailgate&from=..&to=..` |
| F8 | CI: 모델 정확도 게이트(동반 통과 별도 기준), 모델 크기 검사, 펌웨어 빌드, 서버 테스트 | **반드시** | 필수 조건 3 |
| F9 | **대시보드**: 현재 매장 인원, 오늘 누적 입장, 장기 체류 인원(확정값), 알림 목록 | **반드시** | 알림은 외부 채널 없이 대시보드에만 표시 |
| F10 | **장기 체류 기준 설정**: 대시보드 드롭다운으로 선택해 DB에 저장하고, 집계와 알림 판정에 같은 값 적용 | **반드시** | 변경 이력 기록 |
| F11 | **실시간 뷰**: 대시보드 좌측에 ESP32 영상 + 검출 박스 표시 | **반드시** (실패하면 '영상 연결 안 됨'으로 대체) | ESP32 → 브라우저 직결, 서버 경유·저장 없음. 재생 모드에서는 합성 프레임 |
| O2 | 시간대별 입장 차트, CCTV 태그 검색 화면 | 시간이 되면 | API는 반드시 (F7) |
| O6 | 모델이 사람별 박스 크기까지 예측 (CenterNet 방식 크기 회귀) | 시간이 되면 | 기본은 설치 기하로 계산한 고정 크기 박스 |
| O3 | CI에서 Docker 이미지 빌드 | 시간이 되면 | |
| O4 | 실제 카메라 데모(모니터에 모의 영상을 띄우고 촬영) | 시간이 되면 | 실제 카메라 입력 경로까지 검증 |
| O5 | 단순 센서 방식(IR 빔 2개 시뮬레이션)과 비교 실험 | 시간이 되면 | 10단계 비교 실험용 |
| — | 결제 연동, MQTT, PostgreSQL, 외부 알림 채널(Discord 등), 영상 녹화 | **이번엔 제외** | 확장안으로 문서에만 기록 (녹화는 원칙상 제외) |

### 1.3 비기능 요구사항

| 구분 | 요구사항 |
|---|---|
| 개인정보 | 실시간 뷰는 ESP32에서 브라우저로 직접 가고 서버를 거치지 않으며 녹화하지 않는다 (`02-architecture.md` 1.6절). 서버·DB에 저장되는 이미지 바이트 0. 스키마에 BLOB 컬럼을 두지 않고 API는 정의되지 않은 필드를 거부(`extra=forbid`)해서 **테스트로 검증할 수 있게** 한다 |
| 온디바이스 성능 | 5 FPS 이상 (근거: 1.4절) |
| 재현성 | 같은 시나리오를 재생하면 같은 결과가 나와야 한다 (CI 게이트 전제) |
| 시각 기준 | 대조는 **이벤트 발생 시각(시나리오 시각)** 기준. 서버 도착 시각은 쓰지 않는다 |
| 운영 단순성 | 서버는 단일 프로세스(FastAPI + SQLite), 외부 브로커·DB 서버 없음 |

### 1.4 성공 기준 (정량 목표)

모든 정확도 수치는 **직접 만든 합성 테스트 세트 기준**이다. 목표치는 추정이며 첫 측정 후 조정한다.

| 지표 | 목표 | 측정 위치 |
|---|---|---|
| 단독 통과의 인원·방향 정확도 | **90% 이상** | CI (PC에서 TFLite int8 실행) |
| 밀착(2인) 통과의 인원 정확도 | **70% 이상** (별도 게이트) | CI |
| 동반입장 감지 재현율 / 정밀도 | 각각 **80% 이상** (시나리오 20개 내외) | CI 통합 테스트 |
| 장시간 체류 규칙 | 주입한 이벤트 시나리오에서 **100%** | 서버 단위 테스트 (모델과 무관하게 규칙만 검증) |
| 모델 크기 (int8 .tflite) | **256KB 이하** | CI |
| 프레임당 추론 시간 | **200ms 이하** (5 FPS 이상, 추정) → **실측 중앙값 26.3ms** (`04-model.md` 1.7절) | 실기기에서 측정해 heartbeat 로그로 DB에 기록 |
| 이벤트 발생부터 DB 저장까지 | 2초 이하 (LAN) | 수동 확인 |
| CI 전체 소요 시간 | 15분 이하, 게이트 미달 시 실패 | GitHub Actions |

## 2. 결정 근거

- **5 FPS 이상인 이유 (추정)**: 천장에 수직으로 설치하면 머리 높이에서 통행 방향으로 보이는 범위가 약 0.5~1.0m다(천장 높이·화각에 따라 다르며 계산은 `03-hardware.md` 참고). 보행 속도 1.2m/s면 화면을 지나는 시간이 0.4~0.8초이고, 추적하려면 3~4프레임 이상이 필요하다.
- **모의 영상을 microSD/Flash에서 재생하는 이유**: 카메라로 모니터를 찍으면 반사·모아레·노출 때문에 재현성이 떨어진다. 파일 재생은 CI와 같은 입력을 쓰므로 PC 결과와 기기 결과를 비교할 수 있고, 온디바이스 추론 조건도 그대로 충족한다.
- **밀착 통과 게이트를 별도로 두는 이유**: 전체 정확도는 쉬운 단독 통과 샘플이 많아서 높게 나오고, 가장 어려운 케이스의 성능 저하가 가려진다.
- **SQLite + HTTP를 택한 이유**: 1명·3시간 여건에서 브로커·DB 서버 운영 비용을 0으로 만든다 (상세 근거는 6·7단계).
- **장시간 체류를 모델과 분리해서 테스트하는 이유**: 규칙 오류와 카운팅 오류를 따로 진단할 수 있다.

## 3. 대안과 트레이드오프

| 대안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| 공개 사람 검출 모델 사용 (TFLM person_detection, ESP-DL pedestrian) | 학습 시간 0 | person_detection은 사람 유무만 분류해서 위치·인원을 알 수 없음. ESP-DL 모델은 정면·사선 시점 위주라 천장뷰 성능을 보장할 수 없고 무거움 | 기본안은 **자체 소형 모델을 합성 데이터로 학습** (4단계에서 비교) |
| 인원 수 분류 모델 (0/1/2명) | 가장 단순함 | 위치가 없어 방향 판별·추적 불가 | 기각 |
| 실제 카메라로만 데모 | 현실감 | 재현 불가, CI와 연결 안 됨 | 선택 항목 O4 |
| MQTT + PostgreSQL | 확장성, 실무형 | 설치·운영 시간 부족 | 확장안으로 문서에만 기록 |

## 4. 가정

1. 3시간은 설계 + 구현 + 데모 전체 시간이다. (설계만 3시간이라면 범위를 원래 수준으로 되돌릴 수 있다.)
2. 모의 영상은 Python으로 직접 생성하는 합성 천장뷰 그레이스케일 영상이다. 공개 데이터셋은 쓰지 않는다.
3. 서버는 개발 노트북에서 실행하고 ESP32와 같은 Wi-Fi(2.4GHz)에 연결한다.
4. GitHub 저장소를 새로 만들어서 CI를 실행한다.
