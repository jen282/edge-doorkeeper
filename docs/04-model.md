# 04. 모델 설계

## 1. 결정 사항

### 1.1 문제 정의: 머리 중심점 히트맵 검출 + 후처리 추적

| 후보 | 출력 | 방향 판별 | 밀착 2인 | 기기 부담 | 판단 |
|---|---|---|---|---|---|
| 인원 수 분류 (0/1/2+) | 프레임당 인원 | 불가 (위치 없음) | 학습 데이터에 의존 | 작음 | 기각 |
| 사람 유무 분류 (person_detection) | 있음/없음 | 불가 | 불가 | 작음 | 기각 |
| 박스 검출 (SSD/YOLO 계열) | 박스 | 가능 | NMS 때문에 붙은 박스가 합쳐질 위험 | 큼 (앵커, NMS) | 기각 |
| **중심점 히트맵 (FOMO 방식)** | 격자마다 "머리 중심일 확률" | 가능 (추적) | 피크 분리로 대응 | 작음 | **채택** |

크기 정보(박스)는 이 문제에 필요 없다. 필요한 것은 **위치와 개수**뿐이다. 중심점 히트맵은 그 두 가지만 가장 싸게 준다.

### 1.2 입력·출력

| 항목 | 값 |
|---|---|
| 입력 | 96×72×1 그레이스케일, int8 |
| 출력 | 12×9×1 히트맵 (출력 간격 8px, 시그모이드), int8 |
| 격자 한 칸의 실제 크기 | 약 8.5cm (천장 2.7m 가정) |
| 카메라 모드 전처리 | QVGA(320×240) 그레이스케일 캡처 → 96×72 영역 평균 축소 → int8 변환 |
| 재생 모드 전처리 | 없음 (생성기가 96×72 int8로 저장) |

### 1.3 모델 구조 (기본안 A: 자체 소형 CNN)

```
입력 96x72x1
Conv3x3 s2, 8ch, ReLU          → 48x36x8
DWSep s1, 16ch                 → 48x36x16
DWSep s2, 24ch                 → 24x18x24
DWSep s1, 24ch                 → 24x18x24
DWSep s2, 32ch                 → 12x9x32
DWSep s1, 32ch                 → 12x9x32
DWSep s1, 32ch                 → 12x9x32   # 수용 영역 확대 (인접 머리 구분용)
Conv1x1, 1ch, Sigmoid          → 12x9x1
(DWSep = Depthwise3x3 + BN + ReLU + Pointwise1x1 + BN + ReLU, BN은 변환 시 합쳐짐)
```

| 항목 | 추정치 | 비고 |
|---|---|---|
| 파라미터 | 약 5천 개 | |
| 연산량 | 약 1.4M MAC/프레임 | |
| 수용 영역 | 약 59px | 머리(약 20~25px)와 어깨까지 포함, 이웃한 머리와 비교 가능 |
| int8 .tflite 크기 | 약 15~30KB | CI 게이트(256KB) 대비 여유 큼 |
| 사용 연산 | CONV_2D, DEPTHWISE_CONV_2D, LOGISTIC | `MicroMutableOpResolver<3>`, 앞의 두 연산은 ESP-NN 최적화 대상 |

**학습 설정**

| 항목 | 값 |
|---|---|
| 정답 | 머리 중심 주변에 작은 가우시안 (σ ≈ 0.5칸)을 그리고, **가장 가까운 칸이 1이 되도록 정규화**. 정규화하지 않으면 머리가 칸 모서리에 있을 때 최대값이 0.37이라 임계값 0.5를 넘지 못한다(구현 중 발견). 가시 비율 0.5 미만인 머리 주변 1칸은 손실 마스크 |
| 손실 | 가중 BCE (양성 가중치 약 15). 108칸 중 양성은 1~3칸뿐이라 불균형이 크다 |
| 학습 데이터 | 합성 프레임 약 2만 장, Adam, 15~20 에폭 |
| 학습 시간 | 노트북 CPU로 수 분~십여 분 (추정) |
| 양자화 | 전체 정수 PTQ (입출력 int8). 대표 데이터 약 200장 |
| 양자화 게이트 | float 대비 정확도 하락 **2%p 이하** (CI) |

### 1.4 후처리: 피크 검출 → 추적 → 방향 판정 (ESP32에서 수행)

```
1) 피크 검출
   - 히트맵 역양자화 → 임계값 p ≥ 0.5 (검증 세트로 조정)
   - 3x3 지역 최대값만 후보로 남김        # 블롭 연결 방식이면 붙은 두 사람이 합쳐짐
   - 3x3 가중 평균으로 칸 내부 좌표 보정 → 픽셀 좌표 (x, y)
   - 서로 1.5칸(약 13cm) 이내인 후보는 하나로 병합  # 0.25m 간격(약 3칸)은 보존

2) 추적 (트랙 최대 4개)
   - 등속 예측: pred = pos + vel
   - 예측 위치와 검출의 거리 행렬 → 반경 2.5칸 안에서 전역 최적 할당
     (속도를 아직 모르는 새 트랙은 3.5칸: 키 큰 사람이 빠르게 걸으면 8 FPS에서 프레임당 약 23px)
     (트랙 4개 이하이므로 4! = 24개 조합을 모두 따져도 저렴)
   - 할당 실패한 검출 → 새 트랙, 2프레임 연속 놓친 트랙 → 삭제

3) 방향 판정 (가상 라인 2개, 히스테리시스)
   - 통행 방향 축(y)을 세 구역으로 나눔: A (y < 24px, 바깥) | B (중간) | C (y > 48px, 안쪽)
   - 트랙이 A에서 시작해 C에 도달하면 IN, C에서 A면 OUT
   - 트랙마다 최대 1회만 계수. 라인 근처에서 흔들려도 중복 계수되지 않음
   - 화면 중간(B)에서 처음 잡힌 트랙은 가운데 선보다 위면 A, 아래면 C에서 온 것으로 본다
     (빠른 보행자는 A 구역에서 한 프레임도 잡히지 않을 수 있음. U턴은 C에 닿지 않으므로 계수되지 않음)
   - 구현: ml/postproc.py (CI 평가용). 펌웨어 C 구현은 동점 처리 순서까지 같게 맞춘다

4) 이벤트 생성
   - 통과 1건 = passage 이벤트 1개 {ts, direction, conf(트랙 피크 평균)}
   - 트랙 ID는 기기 메모리에서만 쓰고 서버에는 보내지 않음 (궤적 비식별화)
```

**파라미터 근거**

- **보행 시 한 프레임 이동 거리**: 1.2m/s 기준으로 8 FPS면 약 15cm(1.8칸), 5 FPS면 약 24cm(2.8칸)이다.
- **앞뒤 밀착 간격과 겹침**: 앞뒤로 붙은 두 사람의 간격은 30cm(3.5칸) 정도까지 좁아질 수 있다. 예측 없이 반경만으로 할당하면 5 FPS에서 이웃 사람을 잘못 잡을 수 있다.
- **등속 예측을 쓰는 이유**: 예측을 쓰면 잔차가 1칸 안팎으로 줄어든다. 그래서 반경을 2.5칸으로 줄여도 안전하다.

### 1.5 가장 어려운 케이스: 두 명이 붙어서 통과

| 계층 | 대응 |
|---|---|
| 하드웨어 | 천장 수직 설치로 가려짐 최소화. 2.7m 이상 설치로 통과당 프레임 확보 (`03-hardware.md`) |
| 데이터 | 머리 중심 간격 0.2~0.4m인 나란히·앞뒤 쌍을 **전체의 30% 이상으로 과대 샘플링**. 키 차이, 모자, 어두운 머리 등 외형 변이 포함 (5단계) |
| 모델 | 작은 가우시안 정답으로 피크가 번지지 않게 학습. 수용 영역을 59px로 넓혀 "머리 두 개"라는 맥락을 볼 수 있게 함 |
| 후처리 | 임계값으로 블롭을 잇는 대신 지역 최대값 사용. 병합 거리(1.5칸)를 실제 최소 간격(약 3칸)보다 작게 설정. 등속 예측 + 전역 최적 할당으로 ID가 서로 바뀌는 문제 방지 |
| (시간이 되면) 모호성 플래그 | 피크 하나의 히트맵 질량(주변 3×3 합)이 단독 통과 중앙값의 1.6배를 넘으면 `ambiguous=true`로 전송. 서버는 확정 알림이 아니라 "의심"으로 태깅 |
| 알려진 한계 | 아이를 안고 통과하거나 서로 껴안은 경우처럼 머리가 실제로 겹치면 분리할 수 없다. 문서화하고 CI 밀착 게이트에서 제외되는 별도 범주로 둔다 |

### 1.6 추론 프레임워크: TFLite Micro (esp-tflite-micro)

| 항목 | TFLM (채택) | ESP-DL |
|---|---|---|
| 변환 경로 | Keras → `.tflite` int8 (한 단계) | PyTorch/ONNX → esp-ppq → `.espdl` |
| CI 정확도 평가 | **기기에 올라가는 것과 같은 `.tflite`**를 PC에서 `tf.lite.Interpreter`로 실행 | 양자화 모델을 PC에서 평가하는 경로가 상대적으로 복잡 |
| S3 최적화 | ESP-NN 커널 (conv, depthwise) | S3 전용 최적화가 더 공격적이라 더 빠를 가능성 |
| 판단 | 3시간 여건에서 "CI에서 검증한 모델 = 기기 모델"을 가장 쉽게 보장 | 속도가 부족할 때의 대안 |

빌드 환경은 ESP-IDF v5.3을 쓴다. 개발 PC에 v5.3.6이 설치되어 있고 xtensa 툴체인까지 동작하는 것을 확인했다(2026-11-03). 셸에서 `get_idf` 별칭으로 활성화한다. 컴포넌트 매니저로 `espressif/esp-tflite-micro`와 `espressif/esp32-camera`를 받는다. CI에서는 `espressif/esp-idf-ci-action`으로 빌드한다.

### 1.7 메모리·속도 예산 (추정, 실측으로 확정)

**메모리**

| 항목 | 크기 | 위치 |
|---|---|---|
| 모델 (.tflite) | 15~30KB | Flash (rodata) |
| 텐서 아레나 | 최대 동시 활성값 약 42KB (48×36×8 입력 + 48×36×16 출력) + 스크래치 → **96KB 할당** | 내부 SRAM (속도 우선). 실제 사용량은 `arena_used_bytes()`로 측정해 로그에 기록 |
| 재생 프레임 | 추가 버퍼 없음 (Flash 파티션에서 입력 텐서로 직접 읽음) | — |
| 카메라 프레임 버퍼 (선택 O4) | QVGA 그레이스케일 76.8KB × 2 | PSRAM |
| Wi-Fi·LwIP·HTTP 클라이언트 | 수십~100KB 내외 | 내부 SRAM |
| 이벤트 큐 | 64건 × 약 64B ≈ 4KB | 내부 SRAM |
| **합계** | 내부 SRAM 약 250KB 이하 예상 | ESP32-S3 내부 SRAM 512KB 대비 여유 있음 |

**속도 (프레임당)**

| 단계 | 시간 |
|---|---|
| Flash에서 프레임 읽기 (6.9KB) | 1ms 미만 (추정) |
| 전처리 | 재생 모드 0 / 카메라 모드 약 5~10ms |
| 추론 | ESP-NN 사용 시 **약 20~60ms**, 사용 안 하면 150~400ms 가능 (1.4M MAC 기준 추정) |
| 후처리 | 1ms 미만 |
| HTTP 전송 | 별도 FreeRTOS 태스크에서 처리, 프레임 루프를 막지 않음 |
| **목표 합계** | **200ms 이하 (5 FPS 이상)**, 예상 100ms 이하 |

**CPU 클럭**: 실측 결과 ESP-IDF 기본값은 160MHz였다(`03-hardware.md` 1.6절). 위 추정치는 최대 클럭(240MHz) 기준이므로 `sdkconfig.defaults`에 `CONFIG_ESP_DEFAULT_CPU_FREQ_MHZ_240=y`를 넣는다.

**재생 모드 주의**: 재생 모드에서 정확도는 기기 처리 속도와 무관하다. 시각을 프레임 번호로 계산하기 때문이다. 기기 처리 속도는 카메라 모드의 실현 가능성을 보여 주는 지표로 heartbeat에 기록한다.

### 1.8 기기 안정성: 메모리 부하와 다운 위험

**역할 범위**: ESP32가 하는 판정은 **인원 수와 방향 계수까지**다. 동반입장·장시간 체류 같은 이상 판정은 서버가 한다. 후처리(피크 검출, 추적, 라인 판정)는 트랙 4개짜리 고정 배열로 **1KB 미만, 1ms 미만**이다. 기기 부하의 대부분은 추론과 Wi-Fi가 차지한다.

**설계 원칙**: 초기화가 끝난 뒤에는 메모리를 새로 할당하지 않는다.

- 정적 할당 대상: 텐서 아레나, 이벤트 큐, 트랙 배열, JSON 직렬화 버퍼
- 이렇게 하면 프레임마다 메모리 사용량이 똑같다. **첫 프레임이 돌면 1만 번째 프레임도 같은 메모리로 돈다.**
- 동적 할당이 남는 곳은 Wi-Fi와 HTTP 스택뿐이고, 감시도 이 부분에 집중한다.

| 위험 | 원인 | 대응 | 확인 방법 |
|---|---|---|---|
| 힙 고갈·단편화 | 루프 안에서 malloc, HTTP 클라이언트를 매번 생성·해제, cJSON 사용 | 정적 버퍼 + `snprintf`로 JSON 생성. `esp_http_client` 핸들 1개를 재사용(keep-alive) | heartbeat에 `free_heap`, `min_free_heap` 기록. 소크 테스트에서 감소 추세가 없어야 함 |
| 스택 오버플로 | TFLM `Invoke()`가 스택을 사용 | 추론 태스크 스택 16KB, `CONFIG_FREERTOS_CHECK_STACKOVERFLOW_CANARY` 사용 | heartbeat에 스택 최고 수위(`uxTaskGetStackHighWaterMark`) 기록 |
| 서버 다운·Wi-Fi 끊김 | 전송이 막히면서 추론까지 멈춤 | 추론 태스크는 큐에 넣기만 함(대기 시간 0). 큐가 차면 가장 오래된 이벤트를 버리고 `dropped` 카운터 증가. HTTP 타임아웃 2초, 재시도 간격을 늘려 가며 최대 10초 | 서버를 2분 중지해도 기기가 계속 동작하고, 재개 후 정상 전송되어야 함 |
| 워치독 리셋 | 추론 루프가 CPU를 독점 | 추론은 코어 1, Wi-Fi는 코어 0에 고정. 프레임마다 `vTaskDelay`로 양보. 태스크 워치독은 끄지 않음 | 리셋 원인 로그 |
| 브라운아웃 | Wi-Fi 송신 시 순간 전류 + 약한 USB 전원 | 노트북 포트에 직결하고 짧은 케이블 사용 | `esp_reset_reason()` 로그 |
| 아레나 부족 | 아레나를 너무 작게 잡음 | 부팅 시 `AllocateTensors()`를 1회 검사. 실패하면 오류를 로그하고 정지(재부팅 반복 방지) | 사용량(`arena_used_bytes()`) 로그 |

**메모리 여유 (추정)**: Wi-Fi가 켜진 뒤 남는 내부 힙을 250KB 안팎으로 본다. 그중 이 펌웨어의 고정 할당은 약 110KB(아레나 96KB + 큐·버퍼)라서 100KB 이상 남는다. 실측으로 확정한다.

**다운되었을 때의 복구와 기록**

- 패닉이 나면 자동 재부팅한다 (ESP-IDF 기본 동작).
- 부팅 시 `boot` 이벤트를 보낸다. 리셋 원인과 NVS에 저장한 `boot_id`(부팅마다 1 증가)를 함께 실어 DB의 시스템 로그로 남긴다.
- **재부팅 시 잃는 것**:
  - 진행 중이던 트랙: 그 순간 통과 중인 1~2명이 누락될 수 있다.
  - 미전송 큐: 최대 64건.
- **잃지 않는 것**: 매장 내 인원 수. 서버가 DB의 IN − OUT으로 계산하기 때문이다.
- heartbeat가 10초 이상 끊기면 서버가 `device_offline` 알림을 남기고, 그 구간을 "감시 공백"으로 태깅한다.

**검증 (10단계 테스트 계획에 포함)**

| 테스트 | 기준 |
|---|---|
| 소크 테스트: 시나리오 반복 재생 (3시간 일정에서는 10분, 여유가 있으면 30분) | `min_free_heap`이 계속 줄지 않음, 재부팅 0회 |
| 서버 중지 2분 | 기기 생존, `dropped` 값 확인, 재개 후 정상 전송 |

### 1.9 실시간 뷰: 검출 박스 오버레이

**박스는 ESP32에서 직접 그린다.**

- 추론 태스크가 후처리를 마친 프레임을 스트림 버퍼로 복사하고, 그 위에 박스를 그린다.
- 스트림 핸들러(코어 0)가 버퍼를 JPEG로 인코딩해서 보낸다. 인코딩은 `esp32-camera`의 `fmt2jpg()`를 쓴다.
- **프레임과 박스가 항상 일치**하고, 브라우저는 `<img>` 하나로 표시만 하면 된다.

**박스 크기는 모델이 예측하지 않는다.**

- 모델 출력은 중심점이므로, 박스는 **설치 기하로 계산한 고정 크기**로 그린다.
- 어깨 폭 0.45m × 두께 0.26m를 어깨 높이(약 1.45m) 기준으로 투영하면 96×72 입력에서 **약 34×20px**이다.
- 박스 중심은 검출된 머리 중심이다.
- 사람마다 다른 크기를 원하면 **CenterNet 방식 크기 회귀**를 추가한다 (선택 O6).
  - 출력에 너비·높이 2채널을 더하고, 양성 칸에서만 L1 손실을 준다.
  - 정답은 시뮬레이터의 어깨 타원 외접 사각형이다.
  - 모델 증가분은 마지막 1×1 conv의 출력 2채널뿐이다.

**표시 규칙**

| 상태 | 박스 색 | 라벨 |
|---|---|---|
| 추적 중 | 초록 | `#3` (임시 트랙 번호, 기기 안에서만 존재) |
| IN 계수 직후 1초 | 파랑 | `#3 IN` |
| OUT 계수 직후 1초 | 주황 | `#3 OUT` |
| 가상 라인 A, C | 회색 점선 | — |

색을 쓰려면 그레이스케일을 RGB565로 변환해야 한다. 96×72 기준 13.8KB이고 변환 비용은 작다.

**모드별 스트림**

| 항목 | 재생 모드 | 카메라 모드 |
|---|---|---|
| 스트림 해상도 | 96×72 (브라우저가 `image-rendering: pixelated`로 5배 확대) | QVGA 320×240 (박스 좌표를 3.33배로 변환) |
| 스트림 FPS | 8 (시나리오와 같은 속도) | 4로 제한 |
| JPEG 인코딩 | 수 ms (추정) | 20~40ms (추정) |
| 버퍼 위치 | PSRAM | PSRAM (QVGA RGB565 = 153KB) |

**재생 속도**

- 실시간 뷰를 보려면 재생을 **시나리오 FPS에 맞춰 실시간으로** 해야 한다. `CONFIG_DOORKEEPER_REPLAY_REALTIME`의 기본값을 ON으로 둔다.
- PC 결과와의 동치성 확인은 OFF(최대 속도)로 한다.

**자원 영향 (추정)**

| 자원 | 증가량 |
|---|---|
| 내부 SRAM | 두 번째 httpd 인스턴스 스택 약 8KB (버퍼는 모두 PSRAM) |
| PSRAM | 재생 모드 약 30KB, 카메라 모드 약 170KB |
| CPU | 코어 0 (재생 모드에서는 미미함, 카메라 모드에서는 약 15%) |
| 추론 | 코어 1이라 영향 없음 |

**한계**: 카메라 모드로 **실제 사람**을 비추면 박스가 부정확할 수 있다. 모델이 합성 데이터로만 학습했기 때문이다(`05-data.md` 1.4절 도메인 갭). 이번 프로젝트에서 카메라 모드는 모니터에 띄운 모의 영상을 촬영하는 용도(O4)다.

## 2. 결정 근거

- **히트맵을 채택한 이유**: 방향 판별에는 위치가 필수이고, 밀착 2인을 다루려면 블롭이 아니라 피크 단위로 분리해야 한다. 박스 검출은 이 문제에 불필요한 비용이다.
- **자체 소형 CNN을 기본안으로 한 이유**: 합성 데이터에서는 사전학습의 이점이 작다. 반면 CPU 학습 시간과 기기 연산량은 크게 줄어든다.
- **추적을 기기에서 하는 이유**: 서버로 좌표 궤적을 보내지 않고 통과 이벤트만 보내야 비식별 원칙에 맞다.
